## 最影响体验的三个问题

1. **修改/确认安排后，执行交接断开。** 本轮两次普通对话修改都留下取消任务和未结束的选中决策，未见农活命令。`sync_milestone_work`调用`_cancel_goal_children`取消旧计划；该路径没有清理对应`decision.selected`。`_start_accepted_preparation_locked`遇到selected且未finished便返回，不准备替代任务；被取消任务本身又不满足`_ready_step`。18:55的快照仍保留旧decision token和旧requestId。这是本轮真实影响的正常流程问题，不是人为制造的毫秒级竞态。最小改进：在确认旧命令已终结或从未派出后，释放对应旧决策并调度最新授权范围；不能丢弃尚未核实的在途命令。现象本轮重复出现，代码和持久状态支持原因；修复后尚未复验。
2. **把接手/保存说成实际开工。** 次日说“已开始执行”，主动回合还说“原生执行器受理并在跑”，但无原生命令、无动作。最小改进：开始执行的表述必须来自真实派发状态；未派发应说明还在准备或明确阻碍。昨日收获0的回报是诚实的，不能因此忽略开工表述失实。本轮多次出现。
3. **长主动回合阻塞玩家对话。** 次日追问等待约204秒；主动回合约210秒，玩家消息排在后面。最小改进：让已排队的玩家消息及时获得模型处理机会，并缩短重复观察/规划；同时保留当前原生动作的合理收尾。不能仅优化UI状态文字。本轮确认一次长等待，未扩大压力复测。

## 后续代码审计：Mod 对 harness 的适配是否造成阻塞

审计结论：本轮卡死有明确的 Mod 配套 Python 适配/调度层原因。没有证据支持把它归因于 MiniMax harness 无法理解指令或原生游戏动作执行慢。这里的“Mod”包括 C# 游戏端及随包 Python bridge，不把两者混为同一个故障位置。

实际调用链为：游戏 `DispatchLifeChat` → `life.chat.submit` → 独立生活会话（只能观察缓存/保存安排/发控制意图）→ milestone/goal/todo 持久化 → 另一工作会话 `submit_plan` → PlanWorker → C# 原生动作 → outbox → 后续模型回合。C# 日志确认本轮四条农活消息都及时发出了；模型工具记录也包含对应原话和安排修改。本轮阻塞发生在物理命令派出之前。

### 已确认的代码缺陷

1. **取消任务与释放决策不一致。** `work_state.py:1049`在安排描述/约定等签名改变时取消子任务；`_cancel_goal_children`没有同步结束对应decision。`chat_bridge.py:5898`的`_job_in_flight`仅凭selected且未finished就返回true，不检查任务是否已取消。`_start_accepted_preparation_locked`及`_prepare_autonomy_decision`都据此提前返回；PlanWorker又不会执行cancelled任务。`_prepare_autonomy_decision`里的过期决策恢复还位于这个提前返回之后，在该状态下到不了。原始PR #9 HEAD中已有这组逻辑，不是本次回复提前显示补丁新加的。
2. **接续请求可被当成已处理而丢掉。** 当前本地补丁的`_drain_life_queue`先pop准备请求，再调用准备；准备遇到“忙碌/旧决策未结束”只返回说明字符串，调用方不保留请求，也不展示这个阻碍。这是对本地修复的新增审计发现；先前四个测试验证回复顺序和普通排队，没有覆盖“已经选中任务之后再修订”的生产状态，不能据其通过判定闭环已修好。
3. **玩家消息等待来自桥接层的整回合串行。** `life.chat.submit`遇到全局`_busy_lock`直接排队，没有进入当前执行会话。普通C#聊天实际走这个入口；`chat.submit`另一路的主动任务抢占逻辑不能说明UI聊天也有同样能力。Mcode适配器本次通过文件stdin执行一轮`mcode exec`，期间没有给该轮追加玩家消息的路径。不能把这段排队算成模型推理耗时，也不能在未核实各后端接口前宣称底层一定支持某种steer API。

### 接入方式增加的摩擦

- `mcp_server.py:4403`的`protect_job`将直接行动工具也改写为“保存计划并返回job-selected”，并要求模型结束回复后交接；`_assert_decision_valid`限制每个provider回合选一个作业。连续步骤可放入一个计划，限制不是每一步都必须重问，但这确实改变了“调用行动工具→收到实际结果→继续决策”的通常工具循环。
- `submit_plan`的回包写“原生执行器接管”，实际此时只完成持久化，worker仍会被provider和聊天门控阻挡。这种回包会误导反馈。不过生活工具已明确返回`execution=not_started_by_this_tool`，模型仍说“已开始执行”，因此不能把所有错误表述都推给工具措辞。
- C#命令通道只允许一个连接，bridge在整个工作模型回合期间停用PlanWorker，避免409竞争。单演员的动作串行需要保留，但不必让会话、只读观察和整轮模型思考都依附于同一个物理动作连接的所有权。
- 工作工具面有`observe_map_image`，普通对话的`LIFE_TOOLS`没有它。因此恢复C#截图方法并不等于玩家正在说话的那个会话已经能按需看图。尚未实测图片进入模型后的决策质量。
- 所有后端共享上面的工作存储和调度门控；单纯换模型/后端没有消除这处卡死的代码依据。

### 最小原因确认与版本一致性

将相同生产WorkStore代码用于隔离临时目录，保存一个未派出的收获任务，再只修改“收完回屋”的约定：任务从pending变成cancelled，attempts仍0、commandId仍null，selected仍true且finished仍false，ready从true变成false。重新读取该文件，矛盾状态仍在。不改约定的对照保持pending且ready=true。输出在`.local/harness-audit-htvvvklu/diagnosis.json`。

这是对先前实机失败原因的离线确认：未运行游戏、模型、原生动作，也不作为新一轮实机验收。随包的chat_bridge、work_state、companion_milestones、mcp_server、agent_backends、life_chat六个源码文件与本次审计工作区逐一SHA-256相同。

修复方向应收敛为：先修正取消/终态/接续的一致性，确保最新授权不会丢；再减少生活会话和执行会话之间的强制二次规划与状态复制，让既有harness承接对话和工具结果循环。Mod保留游戏真实观察、单演员动作顺序、命令去重与回执，不再用额外“已选中”标志代替实际执行状态。按需截图应进入实际承接玩家任务的工具面。不能简单去掉全局锁：当前每轮还修改进程级环境变量，先隔离调用上下文再缩小锁范围，否则会引入另一类串线问题。

本次审计未改生产代码、未新增付费模型调用；没有把发现这些缺陷表述为已经修复。
